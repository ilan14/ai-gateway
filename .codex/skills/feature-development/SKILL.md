# Feature Development

## 目标与原则

主 Agent 负责整个功能迭代的编排、任务拆分、决策协调和最终集成。

- 遵循项目 `AGENTS.md` 和适用的工程规范。
- 根据任务复杂度选择流程，不机械地调用所有 Agent。
- 用户负责提出目标、约束和验收期望。
- 主 Agent 在用户授权范围内自主处理技术决策、任务拆分和执行协调。
- 遇到需求不明确、技术方案分歧或已有实现时，优先通过调查、分析和验证自主解决。
- 对重要技术决策，应记录选择依据、备选方案和风险，不因存在多个方案而默认请求用户确认。
- 只有无法合理消除的关键业务歧义、超出授权范围的变更或重大不可控风险，才请求用户确认。
- 不以 Agent 数量或文档数量作为完成质量的标准。
- 用户已确认的需求、约束和设计结论作为开发输入，优先遵循；不得擅自改变已明确的业务目标和关键约束。

## Git 开发准备

主 Agent 在开始修改代码或创建交付文档前，按照 `docs/standards/git.md` 检查 Git 状态并准备开发分支。

- 默认从当前分支创建新的任务分支；用户指定基准分支时按指定基准创建。
- 若已位于本次任务对应的开发分支，可直接继续。
- 默认要求工作区干净；不满足条件时暂停自动开发，由用户处理后再继续。
- 分支创建和切换由主 Agent 统一负责，Subagent 不得擅自操作分支。
- 完成分支准备后，再执行需求分析、设计、实现、测试与 Review。

本 Skill 不自动执行分支合并、变基、重置或其他破坏性 Git 操作。

## 一、任务分类与流程选择

### 简单任务

适用于局部 Bug 修复、非行为变更和小范围调整。

1. 分析问题及受影响代码。
2. 实施最小变更。
3. 执行相关验证。
4. 检查 Diff 并汇报结果。

默认不创建完整需求文档，也不强制调用 Subagent。

### 普通功能迭代

1. 分析需求，明确验收标准。
2. 确定实现范围和任务。
3. 调用 Implementer 完成代码实现及基础测试。
4. 根据变更风险调用 Tester 或 Reviewer。
5. 修复发现的问题并重新验证。
6. 汇报结果和剩余风险。

### 复杂功能或架构变更

1. 调用 Architect 分析需求和现有架构。
2. 形成需求与设计文档，由主 Agent 确定并记录重要设计决策。
3. 主 Agent 拆分任务并分配文件所有权。
4. 调用 Implementer 完成实现。
5. 调用 Tester 和 Reviewer 独立验证。
6. 协调缺陷修复、回归测试和必要的复审。
7. 检查完成标准并汇报结果。

## 二、Agent 职责与调度

### 主 Agent

负责：
- 选择适当的开发流程。
- 确定需求目录和交付范围。
- 自主拆分任务，维护任务依赖。
- 为 Subagent 分配任务、输入和文件所有权。
- 协调执行顺序和并行任务。
- 汇总分析、测试和审查结果。
- 组织缺陷修复和最终验收。

### Architect

负责需求分析、现有架构评估、技术方案设计和取舍分析。

在复杂需求或重要架构决策时调用。

### Implementer

负责授权范围内的生产代码实现、基础测试及相关验证。

在需要代码实现时调用。

### Tester

负责独立推导测试场景、编写授权测试代码、执行验证和记录结果。

在需要独立验证时调用。

### Reviewer

负责根据需求、设计方案和代码 Diff 进行独立代码审查。

重点检查：
- 实现是否满足需求和验收标准。
- 代码是否符合设计方案。
- 正确性、并发安全和回归风险。
- 异常处理、资源释放和测试缺口。

重要功能、高风险代码变更和复杂重构应调用。

Reviewer 不负责审查设计方案本身。

## 三、需求分析与架构设计

对于需要正式设计的需求：

1. 主 Agent 确定需求目录。
2. 向 Architect 传递需求目标、约束和目录。
3. Architect 分析现有代码、相关模块及可复用实现，包括相关分支中的已有成果。
4. Architect 明确需求范围、验收标准和关键假设，比较可行方案，创建或更新 `spec.md` 和 `design.md`。
5. 主 Agent 检查设计是否覆盖需求与验收标准，评估方案依据、实现成本及风险。
6. 主 Agent 在授权范围内自主确定方案，必要时要求 Architect 补充调查或修改设计。
7. 对无法自主解决的阻塞事项，按照决策处理规则请求用户确认。

已有实现不应被默认采用或忽略，应根据需求匹配度、实现质量、维护成本和风险决定复用、改进或重新实现。

未经授权，不得擅自执行超出原需求范围的重大架构改造。

### 决策处理与异常升级

主 Agent 负责开发过程中的最终决策，并根据问题性质选择处理方式。

**自主决策**

- 常规工程问题由相关 Agent 在职责范围内处理。
- 重要技术问题由 Architect 分析，主 Agent 决策。
- 信息不足时，优先调查代码、查阅规范、运行验证或要求相关 Agent 补充分析。
- 对影响设计或实现路线的重要决策，在 `design.md` 中记录依据、备选方案、关键假设及风险。
- 不因存在多个合理方案而默认请求用户确认。

**进度告知**

- 对无需用户决策的事项，可以告知发现、决策理由和后续计划。
- 告知不构成流程阻塞，不需要等待用户响应。
- 不得使用要求用户选择或确认的措辞表达非阻塞事项。

**请求确认**

仅在无法自主解决的关键业务歧义、超出授权范围的操作或重大不可控风险下请求用户确认。

- 明确说明待决策问题、备选方案、推荐方案及需要确认的原因。
- 正式请求确认后，必须暂停依赖该决策的后续工作。
- 不得将用户沉默视为同意。
- 可以继续执行不依赖该决策的调查或其他独立任务。
- 子 Agent 发现阻塞事项时，应报告主 Agent，不直接向用户请求决策。

**异常处理**

- 发现现有实现与需求不符时，先分析差异和影响，再决定调整方案。
- 发现设计缺陷时，暂停受影响的实施任务，由主 Agent 协调 Architect 修订设计。
- 无法完成验证时，记录原因和未验证风险，不得宣称验证通过。
- 无法在授权范围内安全继续时，应停止受影响的工作并报告阻塞原因。

## 四、任务拆分

主 Agent 根据需求、设计和现有代码自主拆分任务。

每项任务应明确：
- 目标和预期产出。
- 验收标准。
- 前置依赖。
- 允许修改的文件或模块范围。

拆分原则：
- 优先按可独立交付和验证的功能拆分。
- 不机械地按类、文件或方法拆分。
- 避免过细拆分造成不必要的协调成本。
- 有强依赖的任务按顺序执行。
- 依赖清晰且文件所有权不冲突的任务可以并行。
- Subagent 可以提出任务调整建议，由主 Agent 统一协调。

中大型需求由主 Agent 创建或维护 `tasks.md`。

简单任务不强制创建 `tasks.md`。

## 五、需求目录与交付物

中大型需求使用独立目录：

`docs/specs/<feature-name>/`

目录名使用英文 kebab-case。

根据实际任务需要生成交付文件，不强制每次创建全部文件。

### 文件所有权

- 主 Agent：`tasks.md`。
- Architect：`spec.md`、`design.md`。
- Implementer：授权范围内的生产代码和基础测试。
- Tester：`test-plan.md`、`test-report.md` 及授权测试代码。
- Reviewer：`review.md`。

### 文件写入规则

- 主 Agent 负责指定需求目录、任务范围和文件所有权。
- Subagent 不得自行选择其他交付目录。
- Subagent 直接创建和维护自己负责的交付文件。
- 主 Agent 不代替 Subagent 转写交付文档。
- Subagent 可以读取任务所需的其他文件。
- 未经授权不得修改其他角色负责的文件。
- 共享测试目录必须明确分配文件所有权。
- 不得无协调地并行修改同一文件。
- 需要跨越职责边界时，应先向主 Agent 报告。
- 文档使用中文，保留英文技术标识符。

## 六、代码实现

1. 主 Agent 根据任务依赖分配实现任务。
2. 向 Implementer 提供需求、设计、验收标准和允许修改的范围。
3. Implementer 在授权范围内完成最小、可维护的实现。
4. Implementer 补充相关基础测试并执行必要检查。
5. Implementer 返回修改文件、测试命令、执行结果及剩余问题。
6. 主 Agent 检查实现是否符合设计和任务范围。

发现设计问题时，应向主 Agent 报告，不得擅自扩大需求或偏离已确认的设计。

## 七、独立测试

根据任务复杂度和风险调用 Tester。

Tester 应：

1. 根据需求和设计独立推导测试场景。
2. 创建或更新 `test-plan.md`。
3. 在授权范围内编写或修改自动化测试。
4. 执行相关测试并记录结果。
5. 创建或更新 `test-report.md`。

重点关注：
- 正常路径和边界条件。
- 异常、超时和取消。
- 并发安全和资源释放。
- 回归风险。

测试结果应明确区分：
- 通过。
- 失败。
- 跳过。
- 未执行。

对于失败，应区分产品缺陷、测试缺陷、环境问题和待确认问题。

不得将未执行的测试描述为通过。

## 八、独立代码审查

重要功能、高风险代码变更和复杂重构应调用 Reviewer。

Reviewer 应：

1. 确认审查范围和 Git 比较基准。
2. 阅读需求、设计方案及相关代码 Diff。
3. 检查实现是否符合需求和设计。
4. 检查正确性、并发安全、异常处理和回归风险。
5. 评估测试覆盖情况。
6. 创建或更新 review.md。

Reviewer 不修改生产代码或测试代码。

## 九、并行执行与任务交接

- 优先并行执行真正独立的分析或验证任务。
- 有强依赖的任务必须按顺序执行。
- 并行任务应具有明确的文件修改边界。
- Implementer 与 Tester 不得同时修改同一测试文件。
- Tester 和 Reviewer 可以针对同一稳定代码范围并行验证。
- 若代码或测试文件持续变化会影响验证结论，应改为串行执行。
- Subagent 完成任务后，应向主 Agent 汇报实际产出和未解决问题。
- 主 Agent 根据任务依赖决定后续调度。

## 十、缺陷修复闭环

1. Tester 或 Reviewer 提交问题及证据。
2. 主 Agent 汇总、去重并判断问题优先级。
3. 将确认需要修复的缺陷分配给 Implementer。
4. Implementer 修复并执行相关基础测试。
5. Tester 重新验证受影响的场景。
6. 必要时 Reviewer 重新审查修复后的代码。
7. 主 Agent 汇总最终结果和剩余风险。

测试和审查应基于明确的代码范围。

代码发生相关变化后，应重新验证受影响的部分，不得直接沿用旧代码的验证结论。

## 十一、交付与验收

主 Agent 检查 `AGENTS.md` 的 Definition of Done，确认功能、测试、审查和必要文档满足交付要求。

最后一次影响行为的代码修改后，必须重新执行受影响的测试并通过；Commit 前的测试结果必须对应最终待提交的代码版本，不得使用修改前的测试结果作为验收依据。

### Git 交付

本 Skill 授权主 Agent 在满足交付条件后，按照 `docs/standards/git.md` 自动执行 Commit 和 Push。

1. 检查最终 Git Diff，确认仅包含本次任务相关修改。
2. 检查测试和 Review 结果，确认不存在阻断性交付问题。
3. 按 Git 规范暂存本次任务相关文件并创建 Commit。
4. 将 Commit 推送到对应远程开发分支。
5. 推送失败时停止 Git 交付并报告，不得自行合并、变基、重置或强制推送。

### 最终汇报

主 Agent 应汇报：

- 完成的功能与主要修改文件。
- 测试、代码审查和验证结果。
- 已修复的问题及剩余风险。
- 相关需求与设计文档。
- 开发分支名称、Commit Hash 和 Push 结果。

未成功提交、推送或完成必要验证时，应明确说明实际状态，不得宣称已全部完成。
