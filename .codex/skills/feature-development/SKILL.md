# Feature Development

## 目标与原则

主 Agent 负责整个功能迭代的编排、任务拆分、决策协调和最终集成。

- 遵循项目 `AGENTS.md` 和适用的工程规范。
- 根据任务复杂度选择流程，不机械地调用所有 Agent。
- 用户负责提出目标、约束和验收期望。
- 主 Agent 自主处理常规技术决策和任务拆分。
- 关键需求歧义、重大架构取舍和超出授权范围的变更，应请求用户确认。
- 不以 Agent 数量或文档数量作为完成质量的标准。

## 一、任务分类与流程选择

### 简单任务

适用于局部 Bug 修复、非行为变更和小范围调整。

1. 分析问题及受影响代码。
2. 实施最小变更。
3. 执行相关验证。
4. 检查 Diff 并汇报结果。

默认不创建完整需求文档，也不强制调用 Subagent。

### 普通功能迭代

1. 分析需求，明确验收标准。
2. 确定实现范围和任务。
3. 调用 Implementer 完成代码实现及基础测试。
4. 根据变更风险调用 Tester 或 Reviewer。
5. 修复发现的问题并重新验证。
6. 汇报结果和剩余风险。

### 复杂功能或架构变更

1. 调用 Architect 分析需求和现有架构。
2. 形成需求与设计文档，确认重大设计决策。
3. 主 Agent 拆分任务并分配文件所有权。
4. 调用 Implementer 完成实现。
5. 调用 Tester 和 Reviewer 独立验证。
6. 协调缺陷修复、回归测试和必要的复审。
7. 检查完成标准并汇报结果。

## 二、Agent 职责与调度

### 主 Agent

负责：
- 选择适当的开发流程。
- 确定需求目录和交付范围。
- 自主拆分任务，维护任务依赖。
- 为 Subagent 分配任务、输入和文件所有权。
- 协调执行顺序和并行任务。
- 汇总分析、测试和审查结果。
- 组织缺陷修复和最终验收。

### Architect

负责需求分析、现有架构评估、技术方案设计和取舍分析。

在复杂需求或重要架构决策时调用。

### Implementer

负责授权范围内的生产代码实现、基础测试及相关验证。

在需要代码实现时调用。

### Tester

负责独立推导测试场景、编写授权测试代码、执行验证和记录结果。

在需要独立验证时调用。

### Reviewer

负责根据需求、设计方案和代码 Diff 进行独立代码审查。

重点检查：
- 实现是否满足需求和验收标准。
- 代码是否符合设计方案。
- 正确性、并发安全和回归风险。
- 异常处理、资源释放和测试缺口。

重要功能、高风险代码变更和复杂重构应调用。

Reviewer 不负责审查设计方案本身。

## 三、需求分析与架构设计

对于需要正式设计的需求：

1. 主 Agent 确定需求目录。
2. 向 Architect 传递需求目标、约束和目录。
3. Architect 分析现有代码和相关模块。
4. Architect 创建或更新 `spec.md` 和 `design.md`。
5. 主 Agent 检查设计是否覆盖需求与验收标准。
6. 对未解决的关键需求歧义请求用户确认。

未经确认，不得擅自执行超出原需求的重大架构改造。

## 四、任务拆分

主 Agent 根据需求、设计和现有代码自主拆分任务。

每项任务应明确：
- 目标和预期产出。
- 验收标准。
- 前置依赖。
- 允许修改的文件或模块范围。

拆分原则：
- 优先按可独立交付和验证的功能拆分。
- 不机械地按类、文件或方法拆分。
- 避免过细拆分造成不必要的协调成本。
- 有强依赖的任务按顺序执行。
- 依赖清晰且文件所有权不冲突的任务可以并行。
- Subagent 可以提出任务调整建议，由主 Agent 统一协调。

中大型需求由主 Agent 创建或维护 `tasks.md`。

简单任务不强制创建 `tasks.md`。

## 五、需求目录与交付物

中大型需求使用独立目录：

`docs/specs/<feature-name>/`

目录名使用英文 kebab-case。

根据实际任务需要生成交付文件，不强制每次创建全部文件。

### 文件所有权

- 主 Agent：`tasks.md`。
- Architect：`spec.md`、`design.md`。
- Implementer：授权范围内的生产代码和基础测试。
- Tester：`test-plan.md`、`test-report.md` 及授权测试代码。
- Reviewer：`review.md`。

### 文件写入规则

- 主 Agent 负责指定需求目录、任务范围和文件所有权。
- Subagent 不得自行选择其他交付目录。
- Subagent 直接创建和维护自己负责的交付文件。
- 主 Agent 不代替 Subagent 转写交付文档。
- Subagent 可以读取任务所需的其他文件。
- 未经授权不得修改其他角色负责的文件。
- 共享测试目录必须明确分配文件所有权。
- 不得无协调地并行修改同一文件。
- 需要跨越职责边界时，应先向主 Agent 报告。
- 文档使用中文，保留英文技术标识符。

## 六、代码实现

1. 主 Agent 根据任务依赖分配实现任务。
2. 向 Implementer 提供需求、设计、验收标准和允许修改的范围。
3. Implementer 在授权范围内完成最小、可维护的实现。
4. Implementer 补充相关基础测试并执行必要检查。
5. Implementer 返回修改文件、测试命令、执行结果及剩余问题。
6. 主 Agent 检查实现是否符合设计和任务范围。

发现设计问题时，应向主 Agent 报告，不得擅自扩大需求或偏离已确认的设计。

## 七、独立测试

根据任务复杂度和风险调用 Tester。

Tester 应：

1. 根据需求和设计独立推导测试场景。
2. 创建或更新 `test-plan.md`。
3. 在授权范围内编写或修改自动化测试。
4. 执行相关测试并记录结果。
5. 创建或更新 `test-report.md`。

重点关注：
- 正常路径和边界条件。
- 异常、超时和取消。
- 并发安全和资源释放。
- 回归风险。

测试结果应明确区分：
- 通过。
- 失败。
- 跳过。
- 未执行。

对于失败，应区分产品缺陷、测试缺陷、环境问题和待确认问题。

不得将未执行的测试描述为通过。

## 八、独立代码审查

重要功能、高风险代码变更和复杂重构应调用 Reviewer。

Reviewer 应：

1. 确认审查范围和 Git 比较基准。
2. 阅读需求、设计方案及相关代码 Diff。
3. 检查实现是否符合需求和设计。
4. 检查正确性、并发安全、异常处理和回归风险。
5. 评估测试覆盖情况。
6. 创建或更新 review.md。

Reviewer 不修改生产代码或测试代码。

## 九、并行执行与任务交接

- 优先并行执行真正独立的分析或验证任务。
- 有强依赖的任务必须按顺序执行。
- 并行任务应具有明确的文件修改边界。
- Implementer 与 Tester 不得同时修改同一测试文件。
- Tester 和 Reviewer 可以针对同一稳定代码范围并行验证。
- 若代码或测试文件持续变化会影响验证结论，应改为串行执行。
- Subagent 完成任务后，应向主 Agent 汇报实际产出和未解决问题。
- 主 Agent 根据任务依赖决定后续调度。

## 十、缺陷修复闭环

1. Tester 或 Reviewer 提交问题及证据。
2. 主 Agent 汇总、去重并判断问题优先级。
3. 将确认需要修复的缺陷分配给 Implementer。
4. Implementer 修复并执行相关基础测试。
5. Tester 重新验证受影响的场景。
6. 必要时 Reviewer 重新审查修复后的代码。
7. 主 Agent 汇总最终结果和剩余风险。

测试和审查应基于明确的代码范围。

代码发生相关变化后，应重新验证受影响的部分，不得直接沿用旧代码的验证结论。

## 十一、交付与验收

主 Agent 根据 `AGENTS.md` 的 Definition of Done 判断任务是否完成。

最终汇报应包括：
- 实际完成的功能。
- 主要代码变更。
- 执行的测试和检查及其结果。
- 发现并修复的问题。
- 尚未解决或未验证的风险。
- 相关交付文档位置。

所有 Git 操作遵循 `docs/standards/git.md`。
